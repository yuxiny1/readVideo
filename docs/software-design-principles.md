# readVideo 软件设计准则

本项目以《A Philosophy of Software Design》的核心思想作为长期维护规则：软件设计的首要目标是控制复杂度，重构的价值不在于文件数量，而在于减少修改放大、认知负担和未知依赖。

## 决策原则

1. **长期设计优先于战术补丁。** 每次功能修改都留出一部分时间修正接口、命名、测试或所有权；不把“暂时能跑”积累成默认架构。
2. **模块要深。** 公共接口应小而稳定，实现可以在内部处理复杂分支。只转发参数、迫使调用者理解内部顺序的薄模块没有价值。
3. **隐藏知识，而不只是隐藏代码。** 文件格式、HTTP 载荷、模型错误、路径匹配、重试、状态转换和默认值各自只能有一个权威所有者。相同知识散落在多个模块就是信息泄漏。
4. **把复杂度向下拉。** 通用模块承担校验、默认值和边界情况，让 Controller、组件和调用方保持简单。常见路径应只需要最少参数。
5. **不同层必须有不同抽象。** Controller 表达 HTTP，Message 表达意图，Handler 表达用例，Service 表达领域能力，Storage 表达持久化；Angular 页面表达用户流程，Store 表达状态，API Service 表达传输。
6. **优先形成稍通用的能力。** 模块围绕稳定问题设计，而不是围绕某一次调用硬编码；但不为假想需求建立框架。
7. **定义掉可以避免的错误。** 能通过规范化 URL、缺省配置、幂等复用和安全回退消除的失败，不抛给调用方。真正无法恢复的错误才跨边界，并转换成稳定中文语义。
8. **合并还是拆分取决于知识共享。** 共享大量状态、生命周期和规则的逻辑放在一起；拥有独立知识或独立变化原因的逻辑分开。行数只作为发现问题的信号。
9. **避免透传方法和重复配置。** 若多层只是转交同一组参数，应下沉配置对象或建立更深接口。调用链越长，每层越要增加清晰抽象，而不是复制接口。
10. **先比较两个设计。** 对新增公共边界至少考虑两种方案，比较接口大小、信息隐藏、测试成本和未来修改范围，再选认知负担更小的一种。
11. **代码应当显而易见。** 精确命名、统一约定、短控制流和领域对象优先于技巧。读者不应依赖隐含顺序、神秘布尔值或跨文件猜测。
12. **注释解释抽象和原因。** 公共接口说明契约，复杂算法说明约束和选择理由；不复述代码。难以写清接口注释通常意味着抽象仍不清楚。
13. **复杂度是渐进产生的。** 小泄漏、小重复和模糊命名也要在评审中处理。不能等到模块失控后才进行一次大重写。

## 当前模块所有权

- `backend/services/video_processor.py`：只编排下载、转写、笔记和持久化的任务顺序。
- `backend/services/processing_settings.py`：拥有请求覆盖值、默认值、引擎校验和任务元数据。
- `backend/services/transcription_gateway.py`：隐藏本地 Whisper 与 OpenAI 转写实现差异。
- `backend/services/download_progress.py`：拥有下载进度节流、百分比和日志事件。
- `backend/services/transcript_summarizer.py`：稳定的笔记领域公共入口。
- `backend/services/extractive_summarizer.py`：拥有本地提取式排序算法。
- `backend/services/ollama_client.py`：拥有 Ollama 传输协议和错误翻译。
- `backend/services/ollama_notes.py`：拥有提示词、长文本分块和模型调用流程。
- `backend/services/article_note_parser.py`：拥有模型输出到领域对象的解析规则。
- `backend/services/transcript_segments.py`：拥有原文分块与章节匹配算法。
- `ReaderLibraryViewStore`：拥有 Reader 资料库筛选、排序和计数。
- `ReaderTagEditorService`：拥有当前阅读对象的标签目标、草稿和保存策略。
- `TaskDuplicateService`：拥有历史复用决策和重复任务面板状态。
- `TaskOutputService`：拥有任务收藏与完整笔记复制规则。

## 评审清单

- 修改一个规则是否需要同时编辑多个不相邻模块？如果是，知识所有权可能泄漏。
- 新接口是否比它隐藏的实现更简单？调用方是否必须理解内部顺序？
- 是否能通过更好的默认值、规范化或幂等语义消除异常路径？
- 状态能否由已有信号计算，而不是再保存一份？异步取消和错误是否留在 RxJS 边界？
- Controller 是否只发送 Command/Query？后台长任务是否仍由 worker 执行？
- 新 TypeScript 单元是否有同目录 spec、页面级 provider 和明确生命周期？
- 名称、中文错误和注释是否表达“为什么与契约”，而不暴露实现偶然性？
- 是否存在只透传调用的类、重复常量、未使用字段或为了过测试保留的兼容分支？
